# LoginPage Testing Guide

## What to Test

The `LoginPage` component is responsible for the **presentation/UI of
the login form** and receives its behavior through props:

-   `auth`
-   `setAuth`
-   `onLogin`

The tests should focus on what the user can see and do with the
component.

### 1. Component Rendering

Test that all important UI elements are rendered.

-   Login heading is visible.
-   Email input is visible.
-   Password input is visible.
-   Login button is visible.
-   Register link is visible.

### 2. Email Input

Test the behavior of the email field.

-   Email input accepts user input.
-   Entered email is reflected in the input.
-   `setAuth` is called when the email changes.
-   The email input has the correct accessible label.

Example:

``` tsx
const emailInput = screen.getByLabelText(/email/i);

await user.type(emailInput, "test@example.com");

expect(emailInput).toHaveValue("test@example.com");
```

### 3. Password Input

Test the behavior of the password field.

-   Password input accepts user input.
-   Entered password is reflected in the input.
-   `setAuth` is called when the password changes.
-   The password field is rendered with `type="password"`.
-   The password input has the correct accessible label.

Example:

``` tsx
const passwordInput = screen.getByLabelText(/password/i);

await user.type(passwordInput, "123456");

expect(passwordInput).toHaveValue("123456");
expect(passwordInput).toHaveAttribute("type", "password");
```

### 4. Login Button

Test that:

-   The `Log In` button is rendered.
-   The button is a submit button.
-   Clicking the button submits the form.
-   `onLogin` is called when the form is submitted.

Example:

``` tsx
const loginButton = screen.getByRole("button", {
    name: /log in/i
});

expect(loginButton).toHaveAttribute("type", "submit");

await user.click(loginButton);

expect(onLogin).toHaveBeenCalledTimes(1);
```

### 5. Register Link

Test that:

-   The Register link is visible.
-   The link has the correct destination.
-   The accessible name of the link is correct.

Example:

``` tsx
const registerLink = screen.getByRole("link", {
    name: /register/i
});

expect(registerLink).toBeInTheDocument();

expect(registerLink).toHaveAttribute(
    "href",
    "/auth/register"
);
```

### 6. Props

Test that the component behaves correctly with the props it receives.

The component should correctly use:

``` tsx
auth
setAuth
onLogin
```

For example:

-   `auth.email` should appear in the email input.
-   `auth.password` should appear in the password input.
-   `setAuth` should be called when an input changes.
-   `onLogin` should be called when the form is submitted.

## What Not to Test

Do **not** test functionality that belongs to the parent `Login`
component rather than `LoginPage`.

### 1. Client-Side Validation

Do not test these in `LoginPage.test.tsx`:

-   Empty email validation.
-   Empty password validation.
-   Invalid email validation.
-   Password minimum length.
-   Password maximum length.
-   `"Please fill all the fields"` toast.
-   `"Please enter a valid email address"` toast.
-   `"Password must be between 6 and 10 characters"` toast.

These are implemented in:

``` tsx
validateForm()
```

inside the `Login` component.

Test them in:

``` text
Login.test.tsx
```

instead.

### 2. Axios/API Requests

Do not test:

``` tsx
axios.post(...)
```

inside `LoginPage.test.tsx`.

`LoginPage` does not make the API request.

The API request is made by the parent `Login` component.

API behavior should be tested in:

``` text
Login.test.tsx
```

and mocked using a suitable API-mocking strategy such as MSW.

### 3. Authentication Responses

Do not test these in `LoginPage.test.tsx`:

-   `200 OK`
-   `400 Bad Request`
-   `401 Unauthorized`
-   `403 Forbidden`
-   `409 Conflict`
-   `429 Too Many Requests`
-   `500 Internal Server Error`
-   Network errors.

These belong to the authentication flow handled by `Login`.

### 4. Toast Notifications

Do not test authentication toasts in `LoginPage.test.tsx`.

For example:

``` text
Login successful
Invalid email or password
Too many login attempts
Something went wrong
```

These are generated by the parent `Login` component.

### 5. Navigation

Do not test:

``` tsx
navigate("/home-page");
```

in `LoginPage.test.tsx`.

`LoginPage` does not perform navigation. The parent `Login` component
uses `useNavigate()`.

Navigation should be tested in:

``` text
Login.test.tsx
```

### 6. Backend Behavior

Do not test:

-   JWT generation.
-   Password hashing.
-   Database queries.
-   Authentication middleware.
-   Rate limiting.
-   Express routes.
-   PostgreSQL operations.
-   Backend error middleware.

Those require backend/integration tests rather than `LoginPage`
component tests.

## Recommended Test Separation

### `LoginPage.test.tsx`

Test:

``` text
LoginPage
│
├── Rendering
│   ├── Login heading
│   ├── Email input
│   ├── Password input
│   ├── Login button
│   └── Register link
│
├── User Interaction
│   ├── Email input changes
│   ├── Password input changes
│   └── Form submission
│
└── Props
    ├── auth
    ├── setAuth
    └── onLogin
```

### `Login.test.tsx`

Test:

``` text
Login
│
├── Validation
│   ├── Empty fields
│   ├── Invalid email
│   ├── Password < 6 characters
│   └── Password > 10 characters
│
├── Authentication
│   ├── Successful login
│   ├── Invalid credentials
│   ├── Email not verified
│   ├── Too many requests
│   ├── Server error
│   └── Network error
│
├── Toasts
│   ├── Success
│   └── Error
│
└── Navigation
    └── Navigate to HomePage
```

## Core Principle

> Test **user-visible behavior**, not implementation details.

For `LoginPage`, ask:

> "Can the user see and interact with the login form correctly?"

For `Login`, ask:

> "Does the authentication flow behave correctly when the user submits
> the form?"

This separation keeps the test suite focused, maintainable, and easier
to debug.
